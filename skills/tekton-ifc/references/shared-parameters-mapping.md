# Shared parameters — getting our pset values into real Revit parameters, schedules and tags

Audience: whoever writes the delivery report and walks a non-developer
electrical engineer through Revit. Everything here is Revit UI clicks plus
file formats — no code required on their side.

Evidence tags: **[src]** = Autodesk's open-source Link-IFC importer
(`vendor/revit-ifc`, files under `Source/Revit.IFC.Import/`); **[docs]** =
Autodesk help / IFC Manual; **[project]** = our own artifacts
(`docs/design-ground-truth.md`, KNOWLEDGE.md); **[technique]** = derived
directly from source and awaiting one live confirmation in Revit.

---

## TL;DR

1. **Our psets already become Revit parameters automatically on Link
   IFC.** Every `IfcPropertySet` property is created as an *instance shared
   parameter* on the imported DirectShape, defined in the auto-generated
   `<name>.ifc.sharedparameters.txt` (groups "IFC Parameters" / "IFC Type
   Parameters"), bound to the element's category, shown under the **IFC**
   heading of the Properties palette. [src]
2. **But their names are `PsetName.PropertyName`** (e.g.
   `PanelSchedule.PanelName`, `PanelSchedule.Voltage`) and their GUIDs are
   generated by the importer — so they are *not the same parameter* as the
   firm's `PanelName` / `Voltage` shared parameters, even though our property
   names match the firm's names 1:1. In Revit, two shared parameters with the
   same name and different GUIDs are two different parameters. [src]
3. **Three ways to close that gap** (§4): (A) schedule/tag the auto-created
   `PanelSchedule.*` parameters directly — zero setup, prefixed names;
   (B) **pre-seed the sidecar file** so the importer adopts *our* GUIDs and
   names — the auto-created parameters *become* the firm's parameters
   [technique]; (C) native families with the firm's file (Tier 2).
4. **Revit "Panel Schedule" views (the branded panelboard schedule with
   circuits/breakers) only work for native panelboard families with a
   distribution system.** For imported DirectShapes we use ordinary
   *Schedule/Quantities* views + tags — which is enough for a panelboard
   schedule sheet listing name/voltage/phases/bus/mains/SCCR/circuit count.
5. **Type the psets correctly at export** (`IfcElectricVoltageMeasure`,
   `IfcElectricCurrentMeasure`, `IfcCountMeasure`/`IfcInteger`, `IfcBoolean`,
   `IfcReal`) — the IFC measure decides the Revit parameter's data type. A
   voltage exported as an `IfcLabel` string becomes a Text parameter forever.

## 1. The two files involved

### 1.1 The firm's Revit shared-parameter file (`panelboard-shared-parameters.txt`)

A Revit shared-parameter file is a tab-separated text file with a fixed
skeleton — this is Autodesk's own header, byte-for-byte the format Revit
writes and reads [src: Autodesk's shipped `IFC Shared Parameters-RevitIFCBuiltIn_ALL.txt`
uses exactly this layout]:

```
# This is a Revit shared parameter file.
# Do not edit manually.
*META	VERSION	MINVERSION
META	2	1
*GROUP	ID	NAME
GROUP	1	Panelboard
*PARAM	GUID	NAME	DATATYPE	DATACATEGORY	GROUP	VISIBLE	DESCRIPTION	USERMODIFIABLE
PARAM	<guid>	PanelName	TEXT		1	1	Panel designation	1
PARAM	<guid>	Voltage	ELECTRICAL_POTENTIAL		1	1	System voltage (V)	1
PARAM	<guid>	Phases	INTEGER		1	1		1
PARAM	<guid>	Wires	INTEGER		1	1		1
PARAM	<guid>	BusRating	ELECTRICAL_CURRENT		1	1	Bus ampacity	1
PARAM	<guid>	MainsType	TEXT		1	1	MLO / MCB	1
PARAM	<guid>	MainsRating	ELECTRICAL_CURRENT		1	1		1
PARAM	<guid>	ShortCircuitRatingkA	NUMBER		1	1	SCCR (kA)	1
PARAM	<guid>	Mounting	TEXT		1	1	Surface / Flush / Freestanding	1
PARAM	<guid>	NumberOfCircuits	INTEGER		1	1		1
PARAM	<guid>	NeutralRating	TEXT		1	1		1
```

This is the documented structure of the project's real file (group
"Panelboard", the eleven parameters, and these datatype tokens) [project:
`docs/design-ground-truth.md` §3, KNOWLEDGE.md "Ground truth"]. The literal
file lives in the Design project (`exports/panelboard-shared-parameters.txt`)
and is not vendored in this repo; **the `<guid>` values must be copied from
that file verbatim — never regenerated.** The GUID *is* the parameter's
identity: a re-created file with new GUIDs defines eleven *new* parameters that
no existing tag family, schedule template, or project knows. If the file is
ever lost, export it back out of a project that has the parameters (parameter
GUIDs are stored in the project) rather than retyping it.

Format rules that matter [docs; src `IFCImportCache.ReadSharedParametersFile`,
Autodesk's own files]: tab-separated (not spaces); the `META`/`GROUP`/`PARAM`
header lines and `#` comment lines exactly as shown; `GROUP` column = the
numeric ID of the group row; `DATACATEGORY` normally empty; `VISIBLE` 1 (0 =
hidden helper param); `USERMODIFIABLE` 1. Valid `DATATYPE` tokens include
`TEXT`, `MULTILINETEXT`, `INTEGER`, `NUMBER`, `LENGTH`, `AREA`, `VOLUME`,
`ANGLE`, `YESNO`, `URL`, `MATERIAL`, `IMAGE`, and unit-typed measures such as
`ELECTRICAL_POTENTIAL`, `ELECTRICAL_CURRENT`, `ELECTRICAL_POWER`,
`ELECTRICAL_APPARENT_POWER`, `ELECTRICAL_FREQUENCY`, `ELECTRICAL_ILLUMINANCE`,
`ELECTRICAL_WATTAGE` (Revit's "electrical" discipline specs) [docs Revit
shared-parameter DATATYPE list; Autodesk's IFC files use `TEXT`/`NUMBER`/
`INTEGER`/`YESNO`/`LENGTH`]. Do not hand-edit while Revit has the file open.

### 1.2 The importer's sidecar file (`<name>.ifc.sharedparameters.txt`)

Written automatically next to the `.ifc` on Link IFC [src
`Utility/IFCImportCache.ReadSharedParametersFile`; docs "Link an IFC File"].
Same format; two groups the importer creates if missing — **`IFC Parameters`**
(instance) and **`IFC Type Parameters`** (type). One `PARAM` row per pset
property the import needed, e.g.

```
PARAM	9d1f…	PanelSchedule.PanelName	TEXT		<id of "IFC Parameters">	1		1
PARAM	31ab…	PanelSchedule.Voltage	ELECTRICAL_POTENTIAL		<id>	1		1
PARAM	c2ee…	Pset_ManufacturerTypeInformation.Manufacturer Type	TEXT		<id of "IFC Type Parameters">	1		1
```

Naming rule [src `Data/IFCPropertySetDefinition.CreatePropertyName`,
`ParametersToSet.AddParameterBase`]: `PsetName.PropertyName` for occurrence
psets; the same with a `" Type"` suffix for properties on type objects; the
Revit spec (data type) comes from the IFC measure of the property value.
Naming has varied by processor generation (`Prop(Pset)` in the streamlined
processor) — **always read the names off one imported element** (select a
panel ▸ Properties ▸ scroll to the IFC group) before wiring anything.

## 2. Data-type alignment — decide it in the IFC, not in Revit

| Firm parameter (DATATYPE) | Export the pset property as | Revit imports it as | Do NOT export as |
|---|---|---|---|
| `PanelName` (TEXT) | `IfcLabel` / `IfcIdentifier` | Text | — |
| `Voltage` (ELECTRICAL_POTENTIAL) | `IfcElectricVoltageMeasure` (number, volts) | Electrical ▸ Potential (V) | `IfcLabel '480Y/277 V'` — becomes Text, breaks the datatype match. Put the system string in a separate `SystemVoltage` `IfcLabel`. |
| `Phases` (INTEGER) | `IfcInteger` (or `IfcCountMeasure`) | Integer | text |
| `Wires` (INTEGER) | `IfcInteger` | Integer | — |
| `BusRating` (ELECTRICAL_CURRENT) | `IfcElectricCurrentMeasure` (amperes) | Electrical ▸ Current (A) | `IfcLabel '400 A'` |
| `MainsType` (TEXT) | `IfcLabel` (`'MLO'` / `'MCB'`) | Text | — |
| `MainsRating` (ELECTRICAL_CURRENT) | `IfcElectricCurrentMeasure` | Current | — |
| `ShortCircuitRatingkA` (NUMBER) | `IfcReal` (kA as a plain number) | Number | `IfcElectricCurrentMeasure` would force amperes; keep it a plain kA number to match the firm's NUMBER datatype |
| `Mounting` (TEXT) | `IfcLabel` | Text | — |
| `NumberOfCircuits` (INTEGER) | `IfcCountMeasure` / `IfcInteger` | Integer | — |
| `NeutralRating` (TEXT) | `IfcLabel` (`'100%'` / `'200%'`) | Text | — |

This is the repo-wide convention decided in
`docs/inbox/skill-architect.md` §4: `Voltage` is the numeric measure; the
human-readable system string goes in a separate label property. The v1
sample got this wrong (six `IFCLABEL('480Y/277 V')` voltages) and the
validator flags it.

## 3. What lands in Revit with zero setup (route A)

After **Insert ▸ Link IFC** on our file [src; docs]:

- Each panel is an *Electrical Equipment* DirectShape whose Properties
  palette, under **IFC**, lists `PanelSchedule.PanelName`,
  `PanelSchedule.Voltage`, … plus `IfcName`, `IfcGUID`, `IfcTag`,
  `IfcObjectType`, `IfcSpatialContainer`, `IfcPropertySetList` (a text list
  of the pset names — a handy schedule filter), and the standard psets
  (`Pset_ElectricalDeviceCommon.*` etc.).
- Type-level psets (`Pset_ManufacturerTypeInformation.*`) sit on the
  DirectShapeType (Edit Type).
- Their definitions are in `<name>.ifc.sharedparameters.txt` beside the IFC.

**To schedule them in the HOST project** (the linked values live in the
intermediate file; a host schedule can only show fields the host knows) [docs
IFC Manual "Link IFC": "To schedule parameters from the linked IFC file in the
main project, these must be added to the main project"]:

1. Manage ▸ **Shared Parameters** ▸ Browse ▸ pick
   `<name>.ifc.sharedparameters.txt` (this only *points* Revit at the
   definition file; it changes nothing yet). Group "IFC Parameters" now
   lists `PanelSchedule.PanelName`, etc.
2. Manage ▸ **Project Parameters** ▸ New Parameter ▸ *Shared parameter* ▸
   Select ▸ choose `PanelSchedule.PanelName` ▸ OK ▸ Instance ▸ group under
   **Electrical** (or IFC Parameters) ▸ tick **Electrical Equipment** (and
   Lighting Fixtures / Electrical Fixtures / Specialty Equipment as needed) ▸
   OK. Repeat per field. (Binding to the category is what makes the field
   available to schedules and tags; the values already exist on the linked
   elements and appear as soon as the same-GUID parameter is bound.)
3. View ▸ **Schedules ▸ Schedule/Quantities** ▸ category *Electrical
   Equipment* ▸ Fields tab: add the parameters ▸ **tick "Include elements in
   links"** ▸ filter e.g. `IfcPredefinedType equals DISTRIBUTIONBOARD` or
   `IfcPropertySetList contains PanelSchedule` to keep only panelboards ▸
   sort by `PanelSchedule.PanelName`. That schedule *is* the panelboard
   schedule sheet (one row per panel; add `PanelSchedule.Voltage`, `Phases`,
   `Wires`, `BusRating`, `MainsType`, `MainsRating`, `ShortCircuitRatingkA`,
   `Mounting`, `NumberOfCircuits`, `NeutralRating`).
4. Point Revit's Shared Parameters back at the firm's usual file when done
   (step 1 changed the active file for the session).

Route A works today with zero extra tooling; the only wart is the
`PanelSchedule.` prefix in the field names (rename the schedule column
headings — heading text is free) and that these parameters are *not* the
firm's (different GUIDs), so the firm's existing tag families and schedule
templates keyed on their own `PanelName` don't pick them up.

## 4. Making the imported parameters BE the firm's parameters (route B) [technique]

Read straight from the importer's code [src `Utility/ParametersToSet.AddParameterBase`
+ `Utility/IFCImportCache.ReadSharedParametersFile`]: for each property the
importer looks up `definitions.get_Item(parameterName)` **inside the sidecar
file** first, and only *creates* a definition (with a fresh GUID) when none
with that exact name exists in the group. And the sidecar file is only created
if absent — an existing `<name>.ifc.sharedparameters.txt` is opened and
reused (`fileExisted`). Therefore:

> **If a `<name>.ifc.sharedparameters.txt` already sits next to the IFC and
> already contains, under group `IFC Parameters`, definitions named exactly
> like the parameters the importer would create (`PanelSchedule.PanelName`,
> …) *with the firm's GUIDs*, the importer adopts those definitions — the
> imported values land on the firm's parameter identities.**

Recipe (deliver the sidecar together with the `.ifc`; the skill's harden
step can generate it from the firm's file):

1. Copy the firm's `panelboard-shared-parameters.txt` GUIDs. Write
   `<name>.ifc.sharedparameters.txt` with the standard header, one group
   `GROUP 1 IFC Parameters` (and `GROUP 2 IFC Type Parameters`), and one `PARAM`
   row per property using **the firm's GUID** and the **importer's name**:
   `PARAM <firm-guid-of-PanelName> PanelSchedule.PanelName TEXT  1 1  1`,
   `PARAM <firm-guid-of-Voltage> PanelSchedule.Voltage ELECTRICAL_POTENTIAL  1 1  1`, …
   The DATATYPE must match what the importer would pick from the IFC measure
   (§2) — mismatched types make Revit refuse or duplicate.
2. Place it beside `<name>.ifc` **before** the first Link IFC. The importer
   opens it, finds every name, reuses the definitions (our GUIDs), and appends
   any it needs that we didn't pre-seed.
3. Result: the linked panel's `PanelSchedule.PanelName` parameter has the
   firm's `PanelName` GUID. The firm's *existing* schedules and tag labels
   bound to that GUID resolve the linked values (name in the palette may show
   as `PanelSchedule.PanelName` — the identity is the GUID).

Caveats: name lookup is exact and per-group ("IFC Parameters" / "IFC Type
Parameters"); GUIDs are per-machine only if the sidecar isn't shared — so
**always deliver the sidecar with the IFC** (both files travel together, plus
the `.ifc.RVT` once created). Status: derived from source, one live Revit
confirmation pending — see `docs/inbox/revit-fidelity.md`. Route A remains the
guaranteed fallback.

## 5. Tags

- Any category tag (e.g. an *Electrical Equipment Tag* family) can display a
  shared parameter as a **Label**: Edit the tag family ▸ Modify ▸ Label ▸ Add
  parameter (the little "add parameter" icon in the Label dialog reads the
  active shared-parameter file) ▸ pick `PanelSchedule.PanelName` (route A) or
  the firm's `PanelName` (route B / native) ▸ load into project.
- Tags placed in the **host** can annotate elements in a **linked** model
  (Annotate ▸ Tag by Category, and *Tag All* with "Include elements from
  linked files"). The tag reads the linked element's parameter value.
- What tags cannot do to a DirectShape: leader-to-connector, circuit numbers,
  load values — those parameters don't exist on a DirectShape (no circuits).
  Tag what we authored: name, rating, mounting, kVA, fixture type mark.

## 6. Revit "Panel Schedules" (the special view) — Tier 2 only

Revit's *Panel Schedules* view type (Electrical ▸ Panel Schedules) reads a
**native panelboard family instance** (Part Type = Panelboard/Switchboard,
assigned Distribution System) and its **circuits** (`ElectricalSystem`s) —
slots, breaker frames, poles, loads, phase balancing. A DirectShape has none
of these, and the IFC importer never creates circuits [src, see
`revit-import-fidelity.md` §3]. Consequence: from Tier-1 IFC we deliver the
*panelboard schedule* as a normal Schedule/Quantities view (§3) — the panel
directory data — while the *circuit-by-circuit* panel schedule stays a Design
deliverable (PDF/doc) **or** becomes real via Tier 2 (Design Automation add-in
placing native panelboard families, creating circuits, then Revit's own Panel
Schedule works). Say this plainly in every delivery report so no one goes
looking for a "panel schedule button" that will never light up.

## 7. Type parameters vs instance parameters

- Occurrence psets (`PanelSchedule`, `TransformerSchedule`,
  `SupportSchedule`, `RoomInformation`, `Pset_*Occurrence`) → **instance**
  parameters on each DirectShape.
- Type psets on `IfcXxxType` (`Pset_ManufacturerTypeInformation`,
  `Pset_*TypeCommon`) → **type** parameters on the DirectShapeType (name
  suffix `" Type"`, group "IFC Type Parameters"). Six identical panels sharing
  one `IfcElectricDistributionBoardType` ⇒ one DirectShapeType ⇒ change
  Manufacturer/Model once for all six. This is why the exporter dedupes types
  (`R3 SHARED TYPES`).
- Firm convention: keep schedule-row data (per-panel: name, mounting, circuits)
  as occurrence psets; catalogue data (manufacturer, model, frame) as type
  psets.

## 8. Checklist for the delivery report

- [ ] Export used numeric measures for Voltage/BusRating/MainsRating and
  integers for Phases/Wires/NumberOfCircuits (validator "typed electrical
  values" = 0 warnings).
- [ ] `<name>.ifc.sharedparameters.txt` sidecar generated with the firm's GUIDs
  (route B) and shipped beside the `.ifc`; or the report tells the user to
  schedule `PanelSchedule.*` (route A).
- [ ] Report lists the exact parameter names the user will see and the four
  clicks: link ▸ (Shared Parameters browse) ▸ Project Parameters bind to
  Electrical Equipment ▸ Schedule with *Include elements in links*.
- [ ] Report states: circuit-level panel schedules and connectors are Tier 2.
