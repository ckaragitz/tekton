# ecc-rs-search — algebraic known-plaintext crack of the page ECC (wave 2)

**Result: SOLVED (independently, black-box).** The per-page trailer is
reproduced BYTE-EXACTLY for **3,502 / 3,502 full pages and 55 / 55 final
partial pages** across all six sample files by a pure-Python encoder
derived only from the ground-truth corpus (no DLL). The Reed–Solomon
hypotheses I was tasked with are **refuted**; the code is a **binary
cyclic code** — an *I*-way bit-interleaved Hamming code (BCH family,
t = 1 per lane, burst-correcting up to *I* bits per page):

```
        g(x) = h_m(x^I)   over GF(2),   h_m = min-weight primitive polynomial of degree m
FULL PAGE:  I = 255, m = 11  =>  g(x) = x^2805 + x^510 + 1  (2,805 parity bits)
```

This is the same algorithm the `ecc-intel` agent extracted from
`Utility.dll` (`Foundation\Utility\CRCIO.cpp`, "bit-interleaved reflected
CRCs"). The two implementations were derived by disjoint methods and agree
**for every one of the 64,896 possible page-payload lengths** (identical
parameter class, identical raw size, identical bytes on random payloads) —
see `tests/test_ecc.py::test_implementations_agree_for_every_payload_length`
and `::test_random_payloads_encode_identically`. Reference implementation
of this angle: `experiments/ecc/rs_search.py`.

## 1. The code, precisely

Bit conventions (verified): the page is one bit string read **LSB-first
inside each byte** (bit 0 of byte 0 first, like DEFLATE); the first bit is
the **highest-degree** coefficient of the codeword `C(x)`; `g(x) | C(x)`.
`g(x) = h_m(x^I)` is exactly the *I*-way interleave of the cyclic Hamming
code generated by `h_m` (lane `j` = stream bits `≡ j (mod I)`), so the
systematic parity `P(x) = (M(x)·x^{Im}) mod g(x)` lays the `I·m` lane
parities out row-major after the message automatically.

Layout of every page (full or final), for a payload of `L` bytes:

```
[ payload L bytes ][ Z zero bytes ][ z zero bits ][ w-bit field, LE, value = Z ]
|<---------------- message: s = I*k bits (k rows x I lanes) ---------------->|
[ parity: I*m bits, highest degree first ][ t_pad zero bits to byte end ]
raw page length R = ceil((s + I*m) / 8)
```

* `k` = message bits per lane ("rows"), `k <= K_m = 2^m - 1 - m`.
* The pad is `Z` zero bytes + `z<8` zero bits, followed by a `w = max(4, m-2)`
  bit little-endian field storing **Z** (the pad zero-byte count — this is
  how a reader recovers the true payload end); `8Z + z + w = s - 8L`.
* `t_pad = (-(s + I*m)) mod 8`.

**Full page (L = 64,896):** `(I,m,k) = (255,11,2036)`, `s = 519,180`,
`Z = 0`, `z = 3`, `w = 9` ⇒ the field is nine zero bits ⇒ the observed
**12 leading zero bits** (trailer byte0 = 0x00 and the low nibble of
byte1 = 0), `2,805` parity bits, `t_pad = 7` ⇒ 353 bytes, `R = 65,249`
= the page stride. So the brief's "byte1 = n<<4 (16-value field)" is just
the first 4 parity bits, and the "0/1 last byte" is the single lowest
parity bit sitting alone in the last byte above 7 zero bits.

Class table (`h_m` low exponents; leading `x^m` implied; poly column is the

## 2. Geometry selection (writer's rule) — derived, then reconciled

From the corpus alone I derived, and verified byte-exact on every final
page (`experiments/ecc/rs_search.py::geometry_min_parity`):

1. message bits `M = 8L + w(m)`;
2. if `M ≤ 65·K_m`: stay at the **minimum interleave I = 65** with
   shortened rows `k = ceil(M/65)`; else use **full rows** `k = K_m` and
   `I =` smallest **odd** integer `≥ ceil(M/K_m)` (`I ≤ 255`);
3. choose `m` minimising the parity `I·m`.

Rule 2's *odd I* was the key hidden law: e.g. `Formats/Latest`'s tail needs
only 204 lanes of 2036 bits but the file has **205**; `Global/Latest`
(racbasic) needs 202 but has **203**; every one of the 16 full-row m=11
tails is `ceil(M/2036)` rounded up to odd (100% fit), and every observed
`I` in the corpus is odd. ecc-intel then found the DLL's mechanism: lane
counts above 65 are rounded to a multiple of a class `align` (2; 4 for
m=2) above the 65 floor — identical to "odd" for align 2. The DLL replaces
step 3 by fixed **payload-length thresholds** (`L ≤ 105 → m=4`,
`≤256 → 5`, `≤548 → 6`, `≤1274 → 7`, `≤5081 → 9`, else 11; `≤40 → 3`,
`≤7 → 2`). Both selection rules give the same class on all 55 corpus tails;
they differ only in **222 of 64,896 unobserved lengths** (e.g. L∈[106,~113]
min-parity picks m=4/I=79, the DLL picks m=5/I=65). `rs_search.geometry`
uses the DLL thresholds (authoritative); the min-parity variant is kept as
the documented independent derivation.

## 3. How it was cracked (evidence, byte level)

* **Full-page code identity** (independent big-int check, 5 ms/page):
  `parity = (page_bits · x^{12+2805}) mod (x^2805+x^510+1)`, packed after
  12 zero bits with 7 trailing zeros, reproduces all **3,502/3,502**
  full-page trailers of every stream in every file.
* **Final-page fitter** (`fit_tail`): for each tail, search all
  `(I≤255, m≤12)` for divisibility of the tail bit string (minus its
  trailing zeros) by `h_m(x^I)`. Every one of the 55 tails yields exactly
  ONE `(I,m)` (chance of a false hit ≈ 2^−(I·m)); e.g. `Contents`
  (R=212) ⇒ (65,5); racbasic `Global/PartitionTable` (R=134) ⇒ (71,4);
  dach `Global/DocumentIncrementTable` (R=3949) ⇒ (65,9); `Formats/Latest`
  tail (R=52455) ⇒ (205,11). In all 55 cases a multiple of `I` lies inside
  the ≤8-bit window of admissible parity starts — probability ≈ 12% per
  tail if unstructured, `(0.12)^55` overall ⇒ lane alignment `s = I·k` is
  real.
* **The pad-count field.** The bits between the gzip content end and `s`
  are `Z` zero bytes, `z` zero bits, then a `w`-bit LE integer equal to `Z`,
  ending exactly at `s`. Worked example, `racbasicsampleproject`
  `Contents` (R = 212, s = 1365, (I,m) = (65,5), w = 4): gzip content ends
  at byte 166; bytes 166–169 = `00 00 00 00` (Z = 4); byte 170 = `0xc8` =
  bits (LSB-first) `0,0,0,1,0 | 0,1,1` ⇒ z = 1 zero bit, field bits
  `[s−4, s) = 0,1,0,0` ⇒ V = 4 = Z ✓, then the parity's first bits `0,1,1…`.
  `Formats/Latest` tail: Z = 420 = 0b110100100 ⇒ set bits at
  s−7, s−4, s−2, s−1 — exactly the four `1`-bits observed just before the
  parity block. Cross-file check: rme vs rstbasic `Contents` share
  everything before bit `s−1` and differ from the first parity bit.
* **R matches** `ceil((s + I·m)/8)` for all 55 tails (e.g. `Formats/Latest`:
  `(205·2047 = 419635 + 5)/8 = 52455`), and re-encoding each tail's
  recovered payload with the rule reproduces the stored bytes **55/55**.

## 4. Reed–Solomon / other algebraic hypotheses — REFUTED

`rs_negative_grid` (kept executable) on `Formats/Latest` page 0:

| family | parameters tested | verdict |
|---|---|---|
| A. GF(2^8) systematic RS, interleaved lanes, `nsym×lanes = 350` | (2,175) (5,70) (7,50) (10,35) (14,25) (25,14) (35,10) (50,7) | **structurally impossible**: each lane holds ⌈64896/lanes⌉ > 255−nsym symbols — an RS(255) codeword cannot span it |
| A. GF(2^8), 350 lanes × 1 parity, polys 0x11D/0x11B/0x12B/0x165, fcr 0/1, both symbol orders | 186-byte lanes fit RS(255) | encoded; first 2 parity bytes appear nowhere in the trailer's 350-byte code region |
| B. GF(2^16) single codeword, 32,448 words + 175 parity words | polys 0x1002B / 0x1100B, first root b ∈ {0,1}, word byte order LE/BE, parity order as-is/reversed | encoded (pure-python LFSR); first parity word absent from the trailer |
| C. contiguous CRC/checksum per ~372-byte chunk | (wave-1 result, brief §8) | negative for all common CRC-16/32, Fletcher, Adler variants |

Moot in any case: the trailer is a **binary, bit-oriented** code (the
Autodesk journal reports "rescued N bit(s)"), and the exact GF(2) generator
above reproduces every trailer.

## 6. Unknowns / cautions

* **m = 6, 3, 2 classes** are DLL-sourced only (no corpus page falls in
  their length windows 257–548 B, 8–40 B, ≤7 B). h_3 = y^3+y^2+1 vs the
  reciprocal cannot be checked from data.
* The pure min-parity selection heuristic (this angle) differs from the DLL
  threshold rule for 222 payload lengths (all outside the corpus). Trust
  the thresholds.
* Which streams are ECC-framed is empirical: `Contents`, `Formats/*`,
  `Global/*`, `Partitions/*` yes; `BasicFileInfo`, `PartAtomXML`,
  `TransmissionData`, `ProjectInformation`, `RevitPreview4.0` are stored
  raw (verified: none is a codeword under any (I,m)). Whether Revit keys
  this by stream name or by a stream flag is not established here.
* A logical stream that genuinely ends in zero bytes is ambiguous against
  the writer's zero pad; the format tolerates it (`Z` is what the reader
  strips), but exact round-tripping of *our* output should avoid emitting
  trailing zero logical bytes or must accept them being counted as pad.
