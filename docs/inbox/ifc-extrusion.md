# inbox — ifc-extrusion (`frontdoor --ifc` reads `IfcExtrudedAreaSolid` bodies, #152)

Stream: **ifc-extrusion** (2026-08-09, eng #152). Charter = issue #152: the
IFC intent resolver (`rvt.ifc.intent`, behind `frontdoor author --ifc`) read
geometry only from tessellated face sets / faceted breps, so any file whose
bodies are `IfcExtrudedAreaSolid` — our own tekton-ifc `harden_ifc.py`
output and the dominant body type in Revit/ArchiCAD exports — resolved with
0 walls and equipment without dims while the manifest looked normal. Under
both read backends (real ifcopenshell and the stdlib `steplite` shim).
Territory touched: `src/rvt/ifc/intent.py`, `src/rvt/ifc/steplite.py`,
`tests/test_ifc_intent.py`, `tests/test_steplite.py`,
`tests/fixtures_ifc_extrusion.py` (new, hand-authored), this record, and the
`plugin/lib/**` mirrors regenerated by `tools/sync_plugin.py`. Not touched:
`tools/frontdoor.py`, `src/rvt/frontdoor/base.py`, `skills/tekton-ifc/**`,
`tools/ifc_intent.py`, `inputs/ifc/*`.

## What was built

* **`rvt.ifc.intent`** — `_item_points_tris(item)` is now the body dispatch
  in `_collect_items` (direct items and the `IfcMappedItem` recursion alike):
  tessellated / brep items go to the unchanged `_faceset_points_tris`;
  `IfcExtrudedAreaSolid` goes to `_extruded_points_tris`, which expands the
  profile ring in the solid's `Position` frame, sweeps it by
  `ExtrudedDirection * Depth`, and returns LOCAL prism corners + triangles
  (bottom/top fan caps + side quads). Those ride the *existing* path
  untouched: `world = placement_chain @ local * scale`, `decompose_boxes`,
  `oriented_footprint`, wall runs, equipment dims. A rectangle profile yields
  exactly the 8 corners / 12 triangles the upright-box test recognises.
  Profiles read (`_profile_ring`): `IfcRectangleProfileDef` (XDim × YDim
  centred, honouring the optional 2-D profile `Position`; its rounded/hollow
  subtypes read as the outer rectangle), `IfcCircleProfileDef` (polygonised,
  32 chords), `IfcArbitraryClosedProfileDef` over `IfcPolyline` or
  `IfcIndexedPolyCurve` (with or without `Segments`; `IfcArcIndex` segments
  polygonised on their true circle by `_arc_through`). Inner voids and
  composite/trimmed curves are not read (documented; the consumers use
  extents / footprints / boxes). No new dependency; numpy stays lazy.
* **`rvt.ifc.steplite`** — `_SCHEMA` rows (attribute names verified against
  ifcopenshell 0.8.5 `get_info()` by the new parity test): `IfcSweptAreaSolid`,
  `IfcExtrudedAreaSolid`(+`Tapered`), `IfcProfileDef`,
  `IfcParameterizedProfileDef`, `IfcRectangleProfileDef` (+`Rounded`,
  +`Hollow`), `IfcCircleProfileDef` (+`Hollow`), `IfcArbitraryClosedProfileDef`
  (+`WithVoids`), `IfcCurve`, `IfcBoundedCurve`, `IfcPolyline`,
  `IfcIndexedPolyCurve`; typed-value names `IfcLineIndex` / `IfcArcIndex` /
  `IfcPositiveInteger` (so `seg.is_a()` reads like the real library); and the
  type-object rows `IfcBuildingElementType`, `IfcBuildingElementProxyType`,
  `IfcWallType`, `IfcSlabType`, `IfcElementComponentType`,
  `IfcDiscreteAccessoryType` — the last group is what made
  `hardened.ifc`'s `intent.json` differ between backends *before* this change
  (`typeName` was `null` under steplite for the proxy/accessory types; found
  by diffing the two baseline outputs, fixed here because the DONE demands
  byte-equal backends for that file). `IfcAxis2Placement2D`/`3D` rows already
  existed and are what the profile/solid `Position` slots resolve through.
* **Tests** — `tests/fixtures_ifc_extrusion.py`: a hand-authored IFC4 STEP
  text (zero third-party bytes) — one storey at world (10, 20, 3), a room
  shell whose six named solids cover every profile/curve/Position variant
  (rectangle with a 2-D profile Position, polyline, indexed poly-curve with
  and without Segments, a solid Position rotated 90° about Z, one extruded
  horizontally with Axis = +X), a board with a rotated *placement*, a typed
  board whose body is an `IfcMappedItem`, and a circle-profile accessory —
  plus the expected WORLD boxes / dims / elevations both backends are held
  to. `tests/test_ifc_intent.py` +4 (real library: boxes at expected world
  extents, mapped item + circle, arc polygonisation, full `resolve_intent`:
  4 walls, dims, world-z contract via `level_relative_z`).
  `tests/test_steplite.py` +4 (CI, no ifcopenshell needed: schema rows serve
  the read surface; steplite entities drive the intent reader in-process to
  the same table; `resolve_intent` on the FORCED shim in a subprocess; and a
  real-library parity test on the fixture — every entity/attribute, `by_type`
  closures incl. `IfcRepresentationItem`/`IfcSolidModel`/`IfcCurve`,
  `get_inverse`, placements, psets — that self-skips without ifcopenshell).

## Findings / open questions

* `usecases/chicago-plenum-electrical-room/generated.ifc` (our
  `generate_ifc.py` output) additionally carries `IfcDoor`, `IfcDoorType`,
  `IfcRelVoidsElement`, `IfcRelFillsElement` — doors/openings as first-class
  IFC elements rather than named shell solids. Reading those is #157 / #155
  territory and deliberately not started here; steplite has no rows for them
  yet (they parse, `is_a` works, named attributes would raise).
* Arbitrary profiles are fan-triangulated: correct connectivity and vertex
  set (all the consumers use), not a watertight mesh for concave outlines. If
  a consumer ever needs true faces (e.g. an IFC→mesh export), swap in ear
  clipping there.
