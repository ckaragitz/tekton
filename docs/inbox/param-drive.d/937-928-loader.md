# #937 + #928: the project family loader keeps family names unique and the project names itself

Branch `loader-937-928`, based on `origin/main` 60823f0. Territory:
`src/rvt/famgen/loader.py`, plus one keyword argument at each of the three
front-door call sites (`src/rvt/frontdoor/build.py`, `tools/ifc_intent.py`,
`src/rvt/convert/extract_family.py`). There is one new test module and one
shard drop-in.

## #937: a second family with a name the project already holds

**Before.** `load_family_into_project` never compared the family's name with
the host's `Family` `m_name`s. On 60823f0, loading the flagship panelboard into
`G_ABPD.rvt` and then loading it again into that output wrote a second
`Family` called "Panelboard 480Y/277 400A MCB 42ckt Surface". Revit keeps
family names unique per document, so it would not accept that project. The
validator still reported 0 errors.

**Now (loader).**

- **Survey.** `survey_host` collects every host `Family` name into
  `HostContext.family_names` (case-folded key -> `(id, name)`).
- **Check.** `_author_load` resolves the family's name before it plans or
  authors anything, through `resolve_family_name(name, taken, on_name_clash=)`.
- **`refuse`.** This is the default on both loaders. A taken name raises
  `FamilyNameClash`, a subclass of `LoaderError`. The message names both
  families, for example: "family name clash: the host already holds a family
  named '…' (element N); refusing to load a second family named '…' …". No
  file is written, and the input project is unchanged (sha256 is pinned in the
  test).
- **`rename`.** The family loads as `"<name> (k)"`, using the first free
  k ≥ 2. This is deterministic, so #801's rule holds: identical loads produce
  identical projects. The outcome is recorded in `proofs["family_name"]`
  (`requested`, `written`, `policy`, `clash_with`) and as a line in
  `proofs["plan"]["notes"]`.
- **Batched loader.** `taken` covers the host's names and every earlier family
  in the batch. Under `refuse`, a clash is that family's authoring failure. The
  batch stops there, following the loader's existing prefix rule: the families
  before it are written and `culprit` points at the clash.
- **Case.** Name matching ignores case. This is conservative: a case-only
  variant counts as a clash. Whether desktop Revit treats case variants as the
  same name is **unverified**.

**The front-door decision: rename, never refuse.**

Hard rule 1 says a route always delivers. Refusing would drop the clashing
family from the deliverable (the prefix rule), or drop the whole load. Revit's
own answer to a clash is a dialog, and our routes have nobody to answer it. So
the route takes the non-destructive deterministic answer: it renames the
family and says so. Overwriting the existing family would mean reloading it,
which the loader does not support.

The three call sites below pass `on_name_clash="rename"`. A test pins that by
reading their call sites with AST.

- `build.stage_load_batched`, used by the prompt and IFC builds.
- `tools/ifc_intent.stage_load`, the `add_to_project` chain. Its
  `_slim_proofs` now keeps `family_name`, so the stage record shows any rename.
- `extract_family.reload_family`, the rfa → rvt reload. Its result gains a
  `family_name` entry.

**Does the 6-panel prompt already produce unique names?** Yes. Each name
carries its tag ("Panelboard PP-1 480Y/277 225A MLO 42sp" … "PP-6"), and
families are grouped one representative per family. So the rename never fires
there today. The final `prompt_room.rvt` from
`frontdoor.py author --prompt "an electrical room with 6 panels"` has all 12
CFB streams byte-identical before and after this branch.

A clash can realistically happen in two cases:

- An `--rvt` project that already holds a family we generated before.
- An extracted family named like one of a base's system families. The 2025
  and 2024 bases hold eight curtain-wall families, for example
  "Rectangular Mullion". The 2026 base holds none.

## #928: BasicFileInfo recorded `<out>.pass1.tmp`

**Before.** Every project the loading lane wrote recorded
`"<out>.pass1.tmp"` as its last-save path. Only the nesting path, which passes
`identity=`, re-owned the field.

**Now.** `_commit_and_write` always re-owns `BasicFileInfo` against
`out_path`. It keeps the document GUID and uses the caller's identity, or
`{"username": ""}` when there is none. `own_identity_model` is idempotent on
everything except the path, so the stream is **byte-equal to what
`commit_new_elements` writing `out_path` directly produces**. The test asserts
`raw == identity.own_streams(open_rvt(host), out, identity={"username": ""})[BFI]`
on all three bases. The nesting path is unchanged, because it already took
this branch.

**What changes in the bytes of every loaded project.** Old (60823f0) and new
code were run in separate processes. Each run did a single load and a
two-family batch of the 400 A and 225 A panelboards, into each bundled base.
Same output names in both runs.

| Output | CFB streams | Byte-identical | Differ | BasicFileInfo fields that differ |
|---|---:|---:|---|---|
| `G_ABPD` single / batch | 12 / 12 | 11 / 11 | `BasicFileInfo` | `last_save_path` (`….rvt.pass1.tmp` → `….rvt`), `mirror_text` |
| `G_ABPD_2025` single / batch | 12 / 12 | 11 / 11 | `BasicFileInfo` | same |
| `G_ABPD_2024` single / batch | 12 / 12 | 11 / 11 | `BasicFileInfo` | same |

Front door, 6 panels (2026):

- `_stages/stage_L_loaded.rvt` differs only in `BasicFileInfo`. It now says
  `stage_L_loaded.rvt`.
- `stage_P_identity`, `stage_W_walls` and the delivered `prompt_room.rvt` are
  byte-identical in every stream, because later stages re-own the identity
  anyway.

**Byte-pin tests.** No test pinned a loaded project's bytes or its temp name.
`test_famload_batch` already allowed `last_save_path` as its one identity
difference, and `test_addpath_probes` likewise. Nothing needed re-pinning.
