# famload-2025-lane / #700 — the host survey enters the host's own release

Fragment of the `famload-2025-lane` stream (index:
`docs/inbox/famload-2025-lane.md`, charter issue #14). Nobody else appends here.

## What was built

`rvt.famgen.loader.survey_host` is now a thin wrapper that puts the host's OWN
release in force and delegates to `_survey_host_impl` (the body, moved
byte-for-byte). Nothing else changed.

`rvt.partitions.CONTAINER_CLASS` is rebound by name per release —
`rvt/versions/__init__.py` carries 2026 `0x03A3`, 2025 `0x0391`, 2024 `0x037B`,
2023 `0x0365` — but only while a release context is in force. `survey_host`
relied on the CALLER to enter it, so a bare call compared the 2026 value
against a 2025/2024 header and died in the walker before any family work:

```
ValueError: unexpected Partitions header: v=9 cls=0x391   (2025)
ValueError: unexpected Partitions header: v=9 cls=0x37b   (2024)
```

Read-only instrument, so it takes `global_framing.enter_own_release`'s lenient
ladder — the pattern #671/#696 established for `reduce_v2`'s public entries.

## Two things checked before changing anything

1. **`partitions.py` is not the bug and was not touched.** The issue as I first
   filed it proposed changing the hardcoded constant. That was wrong: the
   mechanism already exists and the failing call succeeds unchanged once the
   release is entered. Correction recorded on #700.
2. **`load_family_into_project` was already correct and is deliberately NOT
   wrapped.** Its body has entered `release_ctx.host_release_context` since
   #14. Verified against unmodified `main`: a bare
   `load_family_into_project(G_ABPD_2025.rvt, …)` returns `ok: True`. A second
   context there would have been redundant — the wrapper I first wrote for it
   was dropped.

So the fix is one function, not the module.

## Evidence

Bare `survey_host` on the three certified bases:

| base | before | after | watermark |
|---|---|---|---|
| `G_ABPD.rvt` (2026) | OK | OK | 1472524 (**unchanged**) |
| `G_ABPD_2025.rvt` | `ValueError` 0x391 | **OK** | 1472448 |
| `G_ABPD_2024.rvt` | `ValueError` 0x37b | **OK** | 1472509 |

Nest-safety: inside a caller's `versions.reading(path)` the watermark is
identical to the bare call, so a survey made during a load is unchanged.

the surveyed watermark, loaded with `place=False`:

|---|---|---|
| load lane | 4 ok / 8 crash | **12 ok / 0 fail** |

## Findings not fixed here

- **`route matrix` still says `rfa -> rvt WORKS` unqualified.** The load lane
  now runs on 2025/2024, but *placement* (`place=True`) is still the #14 lane
  and was not exercised here beyond 2026 — on the bare certified bases it stops
  at `LoaderError: no template instance for placement (host has no instance of
  the family's category)`, which is an honest named refusal, not a crash. The
  matrix row should say what each release actually covers.
- The other read-only entries (`verify_loaded_project(s)`, `provenance_ours`)
  were not wrapped: they are reached through the load path, which holds a
  context. Worth a follow-up if a bare caller ever hits them.
