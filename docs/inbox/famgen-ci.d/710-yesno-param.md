# famgen-ci / #710 — Yes/No family parameters

Fragment of the `famgen-ci` stream (index: `docs/inbox/famgen-ci.md`). Nobody
else appends to this file. Refs #690.

## What was built

`SPEC_YESNO` selects a `ParamDefYesNo` in `add_family_parameter` — one branch
and one constant. `add_family_parameter` previously covered text, integer and
every measurable spec but not Yes/No, the parameter Revit uses for every
visibility toggle, so anything boolean had to be faked as an integer.

## Why this is a law extension, not a guess

Two pieces of standing evidence make the boolean case fall out:

1. **`ParamDefYesNo` is in the 2026 schema with NO own fields** — the same
   shape as `ParamDefString`, which this factory already authors.
   `ParamDefInt` is the one that adds `m_lowBound`/`m_upBound`; that contrast
   is asserted in the test.
2. **The #333 storage-class law** (Revit-2026-born specimen, desktop round 24,
   owner-confirmed): a NON-measurable parameter takes its own `ParamDef` class
   and writes no `m_specTypeId` / `m_restriction` / `m_boundless`; only
   measurable double-valued specs use `ParamDefValue`.

`SPEC_YESNO` is a **selector only** and never reaches the bytes — exactly like
`SPEC_TEXT` and `SPEC_INTEGER`, whose branches also drop the spec id. So no
unverified value is written into any file.

## What this does NOT do

It creates the parameter; it does not associate it with anything. Binding a
solid's **Visible** property still needs the `m_elemPropId` for visibility in a
`FamilyParametrizedElemParamsCell{m_famParamId, m_elemPropId, m_geomTag,
m_bIsSymbol}`. That cell is already generic — connectors drive
`ELEM_PROP_VOLTAGE = -1140002` and `ELEM_PROP_APPARENT_LOAD = -1140005`
through it, both VERIFIED from specimens — but **no visibility property id is
on record anywhere in the repo**, and a fresh clone has no donor family to
mine one from. A user therefore gets correct checkboxes and makes the
associations by hand in the family editor; the first family that comes back
with an associated `Visible` yields the id and closes #690.

## Known rough edge (follow-up, not fixed here)

`make_generic_model` has no way to inject extra family parameters
(`text_params` is text-only), so the panelboard above was built by temporarily
wrapping `FamilyDoc.finalize`. Fine for a probe, wrong for the product — an
`extra_params` argument is the follow-up, recorded on #710.
