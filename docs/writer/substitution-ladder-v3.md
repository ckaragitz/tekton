## 3. The operation — pure IN-PLACE substitution (why it is the cleanest probe)

`rvt.regadd.substitute_elements` (the operation the substitution ladder
actually needs; genesis-addfix).  For a class layer on a PASSING parent:

1. **OUR records** for the layer are built exactly as the X-ladder built
   them — `genesis_substitute.build_X1..build_X9` are IMPORTED unchanged
   (our OBJECTS wired to the parent's own document ids).
2. The X correspondence (old → new) becomes an **IN-PLACE PLAN**
   (`plan_inplace`): each of our records lands in exactly ONE existing
   element ("slot") of the SAME class — its role correspondent (when several
   sample elements share a role, the *primary* = the most-referenced one), or
   without one a free same-class **donor** ranked by inbound reference count
   (**slot-fill**: the sample's 23 materials receive all 13 of ours).  Slots
   landed by an EARLIER rung are protected (the Y2 navigator's viewer can
   never become a slot for a Y9 view's viewer).
3. **Retarget** (`retarget`): every schema-typed ElementId leaf in our
   objects is remapped our-id → slot (never a byte scan); references to our
   records that found no slot HERE resolve by (class, name) against the
   CURRENT file — this is how a Y9 view finds our L1 level in the slot Y8
   landed it in — else through the prior rungs' reports, else are
   neutralised (each reported); `m_id` follows the slot; every re-targeted
   body is proven schema-clean and byte-exact re-encodable BEFORE emission
   (this self-check is what caught the two build hazards of §7).
4. **ONLY the seq-102 OBJECT record** at each slot is replaced (default;
   `seqs` per rung): same ElementId, **same ElemTable row** (episodes /
   owner / vintage byte-identical), same record POSITION in each seq
   stream, same registry slots — **`Global/Latest` (the ADocument) and
   `Global/ElemTable` are BYTE-IDENTICAL to the parent**.  NOTHING is added,
   NOTHING is deleted: the sample's surplus instances and our slot-less
   records are LISTED (residue / not-landed queues), never silently kept or
   dropped.  The rung's ONE variable is the CONTENT of our objects at
   Autodesk's own registrations — the isolation the whole night of X-rungs
   could not achieve.
5. **Certified** per rung: `tools/rvt_validate` 0 errors; the structural
   proof (CRC / ECC / walker / stamps / counts / ISIZE identity);
   four-registry coherence; **registry parity 100 % by construction**
   (Global/Latest byte-identical, ASSERTED); a `rvt.regdiff` registration
   diff on a slot sample (ElemTable row + record positions + id-run + the
   ADocument surface all identical — only the object differs); and the
   `rvt.regadd` **BYTE-DELTA ASSERTION TABLE** vs the parent: only the
   landed slots' seq-102 records changed, the partition stream is the only
   differing stream, no id added / removed, per-seq id order identical —
   every exception listed with its reason (the only ones seen: seq-102
   block re-flow when our objects differ in length, and landed slots whose
   bytes did NOT change because our constructor reproduces the sample's
   empty machinery byte-for-byte).

## 7. Findings (evidence [V] = verified this session) — for KNOWLEDGE.md

1. **The whole substitution can be done with ZERO registration motion**
   [V, 10 rungs]: swapping only the seq-102 object records at existing ids
   keeps `Global/Latest` and `Global/ElemTable` BYTE-IDENTICAL for every
   layer the X-ladder needed (settings, catalog, palette, datum, views) —
   registry parity is a property of the method, not a per-rung assertion
   to get right.  `substitute_elements(..., null=True)` on K4 reproduces
   `Partitions/21` byte-identically (the re-blocker is zero-motion on K4).
2. **In place, the level ↔ plan-view binding decouples from the substitution
   order** [V, Y8/Y9]: X9 had to replace views + levels + phases as ONE
   layer because NEW ids stranded `LevelPlanViewTracking` rows; with ids
   preserved, levels/phases (Y8) and views (Y9) are separate rungs and the
   sample plans keep pointing at the (now our) level ids.
3. **K4's built-in catalog is INCOMPLETE (1,172 / 1,407 keys) and K4 is
   viewer-PASSED** [V]: the K6 "catalog must be COMPLETE" reading was on the
   K1 lineage (retracted); a real, loading file lacks 235 (category, type)
   rows.  Y6 therefore substitutes 1,172 rows 1:1 and does NOT add ours.
4. **Level names live in `m_text`** [V, K4 levels]: `genesis_substitute`'s
   name accessors (`_rec_name` / `name_of`: m_symbolInfo / m_name /
   m_viewName / holders) miss it, so every level keyed to the empty name and
   the first Y9 build pointed BOTH plans at one level.  `_our_record_name` /
   `_file_name_index` add `m_text` and NEVER index empty names (an empty-name
   key collapses every unnamed element of a class onto one id).
5. **`_rewire_subset`'s purge can produce a NON-round-trippable object**
   [V]: on plain K4 (no our-named materials in the file), X9's phasing-
   override references dropped by the purge left `AllProjectPhases.
   m_arrPhasingOverrides` truncated ("need 4 <i, have 0" at re-decode).  A
   record self-check (encode → decode → re-encode byte-exact) BEFORE
   emission is mandatory; this tool's `retarget` refuses such records.  In
   the cumulative ladder the overrides resolve to our Y7 materials by name
   and nothing is dropped.
6. **`build_X9`'s companion sweep is file-wide** [V, K1 X9 report]: it
   collects EVERY Viewer / Viewport / DBDrawing / SunAndShadowSettings in the
   file, including the X2 navigator's OWN constellation — on the K1 ladder
   X9 deleted our navigator's viewer/viewport/drawing (1600009..11).  The v3
   plan protects previously-landed slots and never deletes, so this cannot
   bite here; the X-ladder itself has the latent defect.
7. **Many of our settings constructors reproduce the sample's object
   byte-for-byte** [V]: 40 of Y5's 51 landed slots, 3 of Y3's 5 and Y2's 4
   default browser organizations are byte-identical to Autodesk's own
   objects (empty trackers / machinery with no free value) — the byte-delta
   table lists them as landed-but-unchanged.  For those classes there is
   literally nothing of ours to reject.
8. **Temporary-id determinism is NOT a safe cross-rung key** [V]: every
   rung's context allocates our temporary ids from the same watermark band,
   so a Y6 catalog temp id collides with a Y8 level temp id; cross-rung
   record resolution must be by (class, name) first and only fall back to
   the prior rungs' correspondence WITH a class check.
