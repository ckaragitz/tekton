# THE SUBSTITUTION LADDER (X-rungs) — design, method, and results

Generated by `tools/genesis_substitute.py` (genesis-substitute stream).
Files: `experiments/genesis/subst/` — `X<k>.rvt` + `X<k>.json` per rung,
`probes.json` (the upload manifest), `Xn.json` (the residue check),
`Xn_provenance.json` (the container-layer ledger of the deepest rung).

## 1. Why this ladder exists

Every REDUCTION of Autodesk's sample skeleton LOADS in Autodesk's own
reader (R5, R9, K1, K3, K4, KD1 PASS) and every CONSTRUCTED base FAILS
(G0, G1_candidate, G1a, G1b — and S1..S5, which added OUR settings
singletons + OUR complete catalog to the failing base) with the same
message: 'Revit-DocumentCorruption: The file is corrupt' + 'Design is empty'
+ an extractor crash.  The S-set tested OUR content ON THE SUSPECT BASE and
could not separate "our singletons/catalog are mis-shaped or
mis-registered" from "the G1 base carries an independent defect".

**This ladder isolates by building on the PASSING side.**  It starts from
K1 (Autodesk's empty-project skeleton, 6,540 elements, viewer-PASSED) and
REPLACES its Autodesk-authored content with OUR constructors' output
CLASS BY CLASS, cumulatively, one class(-group) per rung.  Every rung
derives from a PASSING file (K1 or the previous rung), so the first rung
the viewer REJECTS names exactly the one of OUR constructors the reader
disagrees with — and it CANNOT dead-end: whatever survives the ladder is
listed by Xn as the honest work queue.

## 2. What one substitution does (the operator `substitute()`)

For a class C on a passing parent P:

1. **OLD** = P's element ids of class C, grown to their ownership
   constellation (a view's viewer/viewport/drawing/sun; the navigator's
   companions) with a SUBSTITUTION-specific child set (trackers/settings
   that merely REFERENCE the class survive and get re-pointed — see §7,
   finding 2).
2. **NEW** = OUR constructor's records for C, allocated above P's watermark
   in a readable per-rung id band, **WIRED to whatever the OLD elements
   referenced in P** (the navigator's phase/units/sun/workset ids, the
   struct-settings' brace symbol, the sizes tables' catalog keys): our
   OBJECT, the document's WIRING.
3. **CORRESPONDENCE** old → new where a 1:1 ROLE match exists (pen table →
   ours; the per-tree default browser organization → ours of the same
   tree; navigator view/viewer/viewport/drawing → ours by role; a built-in
   catalog row → our row of the same (category, style-type); a material →
   ours of the same ROLE, many-to-one).  OLD ids with no correspondent are
   deleted.
4. Every **SURVIVOR referrer** of an OLD id is RE-POINTED to the
   corresponding NEW id (or neutralised when there is none) through the
   certified byte-exact modify path (`rvt.manipulate` session + record
   re-encode), discovered with the arbiter's own SCHEMA-TYPED ElementId
   decoder — never a byte scan (§7, finding 1).
5. OUR records are appended, the OLD deleted, save-unit 0 re-blocked — all
   through the proven writer path (`commit_new_elements` /
   `commit_plans` / `delete_elements`).
6. **The ADocument (`Global/Latest`)**: every ElementId leaf holding an OLD
   id is REMAPPED to its NEW id IN PLACE (same registry, same slot/key — the
   parity is by construction); unmapped OLD ids are purged with Revit's own
   deletion semantics (positional slot → -1, registry row dropped); OUR
   new-only records (no old correspondent) are registered additively; the
   tree is re-encoded byte-exactly (`rvt.adocument`).
7. **PARITY IS ASSERTED, not assumed**: the registry surface of every OLD id
   (the set of typed leaf paths holding it) is captured BEFORE; AFTER the
   rung the SAME normalized path set must hold the NEW id, positional
   `UniqueElementsTracking` slots must be index-identical, and NO leaf
   anywhere may still hold any OLD id.  P4/P6/K6 proved these registries are
   walked at load, so parity is the whole point of a rung.
8. **CERTIFIED**: `tools/rvt_validate.py` 0 errors (necessary, NOT
   sufficient — the reader is stricter), the structural proof
   (`verify_reduced`: CRC / ECC / walker / stamps / id sets / counts /
   sentinels), four-registry document coherence, ADocument re-decode with
   zero NEW dangling ids, and the parity table — all in `X<k>.json`.

### Why X10 is derived right after X5 (before the catalog) — a finding

A measurement on the X5 base found **1,421 of the built-in catalog rows'
referrers live INSIDE the embedded family documents** (their internal
family-editor views reference the host's built-in styles), plus 238
`Family` / 228 `FamilySymbol` referrers.  Embedded-document records are NOT
editable by the host modify path, so substituting the catalog while the
documents exist would strand ~1,400 references.  Removing the
loadable-family layer + all documents FIRST (K3's usage-null then K4's
coherent four-registry removal — BOTH viewer-PASSED; K4 PASS proved
families are NOT required) leaves the catalog free: on the X10 output only
17 of the 1,407 built-in rows have any referrer at all (~180 host records,
all editable), and **zero** referrers live in documents.  The brief's X10
is therefore derived after X5, and X6.. derive from X10.  Our own
annotation-head families can be re-added later through `rvt.famload` (the
loader L1a PASS proved) once the base itself is proven.

## 4. The correspondence rules per rung (the load-bearing decisions)

* **X1** — the project pen table = the `PenWidthTableElem` with
  `m_famId == -1` (id 2 in every 2026 file); the 8 family-scoped pen tables
  are the curtain systems' and stay.  Registry: 1 leaf
  (`PenWidthTableInfo.m_penWidthTableElemId`).  Referrers: NONE (a byte
  scan is fooled by ~40 geometry-step '2's; the typed walk finds zero).
* **X2** — default-org-of-tree-T → OUR default of tree T (0 views, 1
  sheets, 3 schedules, 4 families); DBViewProject's 4 regen edges and the
  `BrowserOrganizationTracking` type→default map ride on it.  The 7
  non-default sample schemes ('not on sheets', 'Phase', 'Discipline', ...)
  have no correspondent (Autodesk's shipped schemes are theirs) → deleted;
  our 2 house schemes are new-only (appended to the tracking set + a
  system-family-names key).  Navigator view/viewer/viewport/drawing → ours
  by role (DBViewInfo navigator id / views index / DBDrawingInfo ride on
  it), wired to the SAME phases / units / workset-visibility / MEP tracker
  the sample navigator's header edges named.
* **X3** — 1:1 singletons; StructSettings keeps its wiring to the (still
  present) brace/boundary-condition symbols; KeynoteTable OURS = EMPTY
  (Autodesk's shipped 3,840-row keynote database is NOT reproduced);
  InitialViewSettings keeps the starting view.  The RvtLinkInstance that
  names the keynote table is re-pointed.
* **X4** — settings singletons keep the sample's per-classification pipe /
  duct TYPE wiring and the wire leader/tick symbols; the SIZE TABLES are
  OUR DATA (SMACNA duct series; ASME B36.10M/B36.19M + ASTM B88 pipe
  dimensions — published facts authored in the tool; NEC 310.16/250.122/
  310.15 ampacity) keyed onto the parent's still-present catalog symbols by
  normalized NAME ('Aluminium' → our Aluminum; steel / non-magnetic
  conductors and the 60 °C column get NO rows: our standard defines none —
  documented, not an omission).  The MEP catalogs themselves stay (a later
  rung).  The MEP trackers' regen edges into the duct/pipe settings are
  re-pointed.
* **X5** — assembled class by class from the standard constellation
  (never `standard_settings(tier="all")` blindly — its internal wiring
  would re-create the X4 classes; the MEP tracker constellation is wired
  to OUR X4 duct/pipe settings read from the CURRENT file).  Multi-instance
  sets pair by name (sequences 'Numeric'/'Alphanumeric', graphics styles
  '<Shading>'/'<Raytracing>', area schemes by area-type code); where ours
  has fewer instances (print setups 3→1, worksharing display 2→1) the extra
  sample instances are deleted.  RULE: X5 never introduces a CLASS the parent
  lacks (ours-without-old-counterpart are NOT added — a class the passing
  skeleton never carried would be a new variable), and every settings class
  WITHOUT a constructor is LISTED as residue, never silently kept as ours.
* **X6a** — the perfect 1:1: K1's project built-in rows are exactly the
  1,074-projection + 333-cut ENUM our `catalog.builtin_style_catalog`
  generates (an interface constant); each old (category, type) row → our row
  of the same key.  The 1,409 `CategoryTracking` category→style registry
  leaves (the map P4/P6/K6 proved is walked at load) are remapped in place.
* **X7** — many-to-one by ROLE keyword (documented rules): their many
  'Dash' variants → our one dash pattern; a zero-grid pattern IS a solid
  fill (structure) → our solid; 'Concrete 10 MPa'/'Default' → our concrete;
  'Phase - Demo' → our demolition-phase material...  Wall/floor/roof types,
  pipe segments, phase filters, colour-fill schemas and the residue
  subcategory styles are re-pointed by role or neutralised (-1 = solid /
  by-category).  The materials' companions (131 AppearanceAssetElem naming
  Autodesk's asset library, 56 PropertySetElement thermal/physical sets,
  the PropertySetLibrary) are deleted with them — our materials carry none.
  Two OPEN TOKEN questions ride on X7 (probe rows): our solid fill under
  our own name (not `<Solid fill>`), and no `'Default'`-named material.
* **X8** — units / true-north / project-info 1:1; the sample's PROJECT
  geo-location (the one our X5 `ActiveGeoLocationTracking` names as project
  position) → our project location + its site → ours; the other → our
  internal ones; base points by role (`m_bShared` = survey point).  The 144
  referrers re-pointed are mostly the regen edges into the units (the
  highest fan-in element in the document).
* **X9** — ONE coherent replacement (plan views are BOUND to levels, so
  the view and datum layers cannot be substituted separately): the sample
  project view → ours; its `'{3D}'` default 3D view → our 3D view; the
  floor plans of the two lowest building storeys → our two plans, and THOSE
  plans' levels (read from the plan's `m_genElemId` = generating datum) →
  our L1 / L2; phases by sequence order; filters by role name; the 19
  project view types by `m_systemFamilyIdx`; the default system text type →
  our body text.  Everything else in the view/level/phase layer is deleted;
  the DBView registries (project view, views index, `LevelPlanViewTracking`
  level→plan map, `DBViewTypesForNewLevel`, `SymbolIdMgr` defaults) are
  re-pointed or purged.  The house-catalog subset is RE-WIRED to the
  current file (levels → the X8 units / geo-location by class-uniqueness;
  the phasing overrides → the X7 phase materials + patterns by exact name).

## 5. What the parity assertion CAUGHT (findings, not bugs swept away)

The parity table is not decoration.  On X9's first build it FAILED with
two GENUINE registry defects that the validator (0 errors) did NOT see:

1. `LevelPlanViewTracking.m_levelIdToPlanViewIds` (a level → [plan views]
   map): the plan→level lookup used the wrong field, the fallback mapped a
   level with no plan, and the map row keyed by the real plan-2 level was
   dropped with its (unmapped) level — orphaning our plan 2 from the
   registry.  FIX: a plan's level is `DBViewPlan.m_genElemId` (its
   generating element) [VERIFIED]; the level correspondence is now DERIVED
   from the mapped plans, and the map holds our L1 → our plan 1, our L2 →
   our plan 2.
2. `UniqueElementsTracking` slot 43 (our X3 `InitialViewSettings`) went
   EMPTY: the reduction ladder's ownership set (`V2_CHILD_CLASSES`) treats
   trackers that REFERENCE seeded content (InitialViewSettings names its
   start view) as children that die with it — correct for a reduction,
   WRONG for a substitution.  FIX: `SUBST_CHILD_CLASSES` (§7 finding 2) —
   view-referencing trackers survive and get their references re-pointed.

Both were caught ONLY because parity is asserted, and both are exactly the
class of registry mis-registration this whole workstream exists to
eliminate.  This is the strongest argument for the method.

## 7. New findings for KNOWLEDGE.md

1. **Reference discovery MUST be schema-typed, never a byte scan** [V]:
   `manipulate.referrers()` / `candidate_referrers()` byte-scan the LE-i64
   of an id and are FOOLED for low ids — the project pen table's id 2 gets
   ~40 false "referrers" (`m_faceHistTable[].m_id`, `m_idCounter`,
   `m_latestGStepTypeInPrevRegenCycle[]` = geometry-step type codes /
   counters), while the arbiter-typed graph (`rvt_reduce.build_state_v2` /
   `validate._RefDecoder`) correctly finds NONE.  For any id below ~10^5
   the untyped path is unsafe.  The typed walk
   (`genesis_assemble.AdocGraphEditor.iter_leaves`) works on ANY class
   body — element records included — and yields in-place-mutable leaves;
   `genesis_substitute.TypedEditor` wraps it for remap / purge / surface.
2. **Ownership growth differs for substitution vs reduction** [V]:
   trackers / settings singletons that merely REFERENCE content
   (InitialViewSettings → its start view, AllPlanTopologies → levels,
   GCSTracker, HubsTracker, PostedWarningElem, RegenSplitterElem,
   SelectionFilterElement, ScheduleInstanceBaseOnSheetsTracker) must be
   EXCLUDED from a substitution's constellation (they survive, references
   re-pointed); the reduction ladder's `V2_CHILD_CLASSES` correctly kills
   them.  `SUBST_CHILD_CLASSES = V2_CHILD_CLASSES − {those}`.
3. **A plan view's level is `DBViewPlan.m_genElemId`** (its generating
   datum; also duplicated in `m_pPlanViewRange2.m_viewDepthPlaneLevelIds`)
   [V rstbasic plan 245443 → level 245423].  There is no `m_levelId`.
4. **`LevelPlanViewTracking.m_levelIdToPlanViewIds`** [V]: a level →
   [plan view ids] map (one row per level, empty list allowed) — a load-
   walked registry both the level AND the view layer index; substituting
   either without the other strands rows.  Views + levels + phases are
   ONE coherent skeleton substitution for this reason (X9).
5. **The built-in object-styles table = exactly the graphic-category
   ENUM** [V, K1]: the project-level built-in `GStyleElem` rows of a real
   file are exactly the 1,074-projection + 333-cut set our catalog derives
   as a per-release constant — the catalog substitution is a true 1:1.
6. **Embedded family documents PIN the host's built-in catalog** [V]:
   1,421 typed edges from records INSIDE embedded documents into the host's
   built-in style rows (family-editor views' style refs) on the X5 base;
   they vanish only when the documents are removed → the family/document
   removal MUST precede any catalog substitution (order finding above).
7. **The four-registry document removal composes with a substituted
   settings layer** [V, X10 VALID on the X5 base]: K3's usage-null +
   K4's units/ContentDocuments/ContentTable/FamilyMgr reconciliation ran
   unchanged over our X1..X5 substitutions with 0 residual GUID bytes.
8. **The MEP catalog symbol names differ from ours by spelling / scope**
   [V]: K1's wire catalog = Copper / **Aluminium** / Steel / Non-Magnetic ×
   60/75/90 °C; ours = Copper / Aluminum × 75/90 (NEC).  A settings table
   keyed onto their catalog must normalize names ('aluminium'→'aluminum')
   and DOCUMENT the uncovered symbols (steel / non-magnetic / 60 °C get no
   rows) rather than invent data for them.
9. **`standard_settings(tier="all")` is NOT sliceable by class** [V]: its
   MEP tracker constellation is wired to its OWN duct/pipe settings; taking
   a class subset strands those edges.  Assemble a subset class by class,
   reading the wiring from the CURRENT file (X5's rewrite).
10. **Registry parity + validator-clean are DIFFERENT gates** [V, X9]: two
    real registry defects (findings §5) passed the validator with 0 errors
    and were caught only by the before/after parity table.  Every future
    generator that touches an ADocument registry should assert parity.

## 8. Reading the viewer verdicts (also in `probes.json:reading_the_results`)

Upload the rungs IN DERIVATION ORDER (`upload_order`: X1, X2, X3, X4, X5,
X10, X6a, X7, X8, X9); each is cumulative.  The FIRST rung that FAILS
while its parent PASSED convicts exactly the class group that rung
substituted — one of OUR constructors, named in the rung's
`class_substituted`; the rung's report carries the field-level
correspondence + parity table to diff.

* **X1 FAIL** → our PenWidthTableElem (S1's own class): diff our pen table
  vs Autodesk's id 2 field by field.
* **X1..X5 all PASS** → EVERY settings-singleton constructor we own is
  reader-accepted on the passing skeleton ⇒ the S5-set's FAIL on G1 was
  the G1 BASE, not our singletons.  The singleton layer is retired.
* **X10 FAIL** → an interaction between the (K4-proven) removal and one of
  our X1..X5 substitutions (K4 itself PASSED on the pure sample).
* **X6a FAIL** → OUR object-styles catalog is what the reader rejects — the
  first attributable answer to the S4/K6 question; candidates: a (category,
  type) row a real project never carries, a validated value (pen range /
  colour), the CategoryTracking row shape.
* **X7 FAIL** → our patterns / materials; bisect patterns vs materials;
  test the two name tokens ('<Solid fill>', 'Default').
* **X8 FAIL** → units (highest fan-in) vs site / base points vs project
  info.
* **X9 FAIL** → OUR skeleton layer (levels / phases / views) — the layer
  G0/G1 were BUILT from and the most likely home of the constructed-base
  defect; bisect X9a (view types) / X9b (views) / X9c (levels + phases),
  reading the card message each time.
* **EVERYTHING PASSES** → every constructor we own loads; the genesis base
  is X9 minus the Xn residue (the work queue in §6) plus the container
  layer (own-save / counsel).
