## A. Plugin / skill-path latency (first-class per steer #108)

**Where we stand (measured 2026-08-09, bare unzip + system python3, cloud VM):** `go author --prompt "an
electrical room with 6 panels"` = **22.2 s cold / 21.8 s warm** end to end (READY, per-release flat);
a 1-panel prompt ≈ 6 s; preflight 0.045 s; per simulated skill session `surface_bench` cowork 17.0 s /
codeexec 15.2 s (8 calls). The job is **build-dominated (~20 s)**: each generated family's load stage costs
~2.5 s, so equipment count drives wall time (#124). Import weight was the second lever: the prompt-only path
eagerly imported ifcopenshell (+numpy/shapely/lark) — fixed in PR #141 (`import rvt.frontdoor.build`
376 → 52 ms; process import time 423 → 200 ms; cold bare `go author` 20.1 → 18.8 s); the numpy-free ECC
engine from PR #128 removed another ~3 s cold (19.7 → 16.9 s on that engineer's box). Every latency item is
only *done* with a measured before/after from a bare surface (S-2026-08-09-g).

**Done, for a user:** a one-sentence request returns a delivered file in well under 10 s for a typical
room on any surface, in ONE tool call whose JSON already carries paths, per-release status and caveats
(no follow-up calls), with the skill layer's eagerly loaded text small enough not to tax the model.

**Staged path:** (1) measure + guard — surface perf tests execute in CI (#136), latency numbers in every
latency PR; (2) the big lever — per-family load stage cost (#124: cache/parametrise the famdoc build,
share the four-registry walk across N families, avoid re-decoding the base per family); (3) startup —
remaining eager imports (#139 xml.sax → urllib/http/ssl), schema-cache load, python discovery; (4) round
trips — one-call `go` results that carry the honest status block (#24), progressive references.

**Issues:** #6 (PR #141), #124, #139, #136, #24, #92 (PR #126), #75 (PR #128), #110, #125, #127.

## B. Genesis: native creation from a prompt

**Where we stand (evidence, measured 2026-08-09 on a fresh cloud clone):** `frontdoor author --prompt "an electrical room with 6 panels"` builds in 30 s on the pinned composed base G_ABPD (sha 84173b89…): 4 walls, 6 Eaton PRL2X panelboard families generated, loaded (four-registry) and placed, ElemTable 3102→3220, validator 0 errors, identity ours — and the same prompt with `--target-version 2025/2024` produces native 2025/2024 files with the same census and 0 errors. That is real backwards compatibility at the engine level. What Autodesk's reader has actually certified is narrower: walls (LOAD, and RENDER when the seq-103 solid is authored) on 2026 and 2025; loading Revit-born .rfa and extract→place; nothing front-door-shaped on 2024 yet; and the one open cell — our generated famdocs + placed instances on our composed bases (verdict #48, #16) — is exactly what every equipment prompt produces. **Done, for a user:** one sentence naming a room, storeys, service gear, lighting and feeders yields — for the Revit year they named (2026/2025/2024, 2023 after compose) — a file that opens on a plan/3D view framing the room, with visible walls, named levels, a Space, placed and circuited equipment whose panel schedules regenerate, ProjectInfo carrying their project name, and a manifest whose stamps match the ledger cell by cell.

**Staged path:** (1) honesty first — re-key the degrade policy on the real open cell and fix the self-baselined G1 gate (PG1); (2) make what is already certified visible and identified — wall solids in the front door, ProjectInfo from the intent, per-release evidence in the matrix, and one three-release walls batch to bring 2024 to parity (PG4/PG6); (3) grow the native element roadmap in MEP priority order, each as constructor/CONSTRUCTED specimen + validator law + prompt grammar + matrix evidence, certification as its own single-variable viewer round with a byte-identical control: circuits → levels/per-level placement → luminaires → spaces → (later) panel schedule views, grids, doors/hosting, receptacles/conduit; (4) instance-bearing kinds inherit #16's verdict — they stop at validator-green + STAGED until the desktop-Revit dialog names the failing class, and meanwhile ride the certified add_to_project cell for real user projects.

## C. IFC → RVT conversion

**Where we stand (evidence):** IFC → RVT today is a proven lane for exactly one dialect: the tessellated, world-baked IFC4 our own three-d-stage/frontdoor writers emit. On that dialect the route is honest and complete for an electrical room: `frontdoor author --ifc electrical-room-2500a.ifc --target-version 2025` delivers a 2025 .rvt in 43 s (IFC read is 1 s of it), validator 0 errors, 4 walls + 8 placed boards/transformer generated from the Pset tagging contract, every unmapped item (ground bus, conduit run, hangers, service) named as a degradation, walls+families stamped PROOF-ONLY per the open cell, and the stdlib steplite reader produces a byte-identical intent. Certified depth: V25/V26 room-from-IFC (walls), family load lineage. The moment the IFC is not that dialect the lane degrades silently: our own tekton-ifc `harden_ifc.py` output (extrusions) loses all 4 walls and 9/10 bodies with no manifest line saying so; a Revit-style file (IfcWallStandardCase + IfcExtrudedAreaSolid, IfcDoor, IfcSpace, two storeys, mm) resolves units and levels correctly and still places the board from its placement chain, but builds no wall, drops the space, puts everything on the base's L1, and under steplite the door vanishes from the census. rvt->ifc exists and round-trips 8/8 + 4/4 on our output, but only inside a release context — the CLI fails on any 2025/2024 file — and the matrix still says 'missing'.

**Done, for a user:** hand Claude an IFC exported from Revit 2020–2026 (IFC2x3 or IFC4), ArchiCAD, or our own skill, name the recipient's Revit year, and get back a .rvt for that year in which storeys are levels, walls are walls (openings at least recorded, later cut), spaces are rooms, distribution boards/transformers are our parametric families carrying the schedule values, trays/conduits are recorded runs (native later), and the manifest carries a census of everything read, mapped, recorded-only, or dropped — with the reason — so the engineer doing QA knows what to check. The reverse (rvt->ifc) works on any release we write so round-trip survival is the regression oracle.

**Staged path:** (1) honesty first — an IFC census law in every manifest and a hand-authored, zero-third-party conformance fixture set that runs under steplite in CI; (2) geometry breadth — IfcExtrudedAreaSolid + profile support in intent and steplite, steplite closure/schema parity for foreign classes; (3) semantic breadth in MEP priority order — storeys->levels, IfcWall->WallRun, IfcSpace->room, boards without catalog rows -> house family, trays/conduits when conduit types exist in the base; (4) backwards compatibility — IFC2X3 intake and release-aware convert CLIs so 2024/2025 outputs round-trip; (5) scale — linear-time steplite with a measured 3 MB/2000-product baseline. Viewer certification of each new built shape rides the normal STAGE->human-upload loop.

## D. RFA / families

**Where we stand (evidence):** The generator is real and sample-free: `tools/make_family.py panelboard|transformer|luminaire` composes an Electrical Equipment or Lighting Fixtures family from the manufacturer facts store (7 cited lines: Eaton Pow-R-Line and dry-type, Square D NQ/NF, HPS, Lithonia BLT/LDN6, generic devices; `catalog validate` 7/7 OK) into a ~217 KB .rfa in ~2 s whose every byte is ours or the per-release schema constant — family-mode validator 0 errors, provenance 11/11 clean, our BasicFileInfo/PartAtom, the mandatory 0x0f3f footer blob. Parameters are real type parameters (the eleven tagging-contract names plus Width/Height/Depth, Manufacturer/Model as values, assumed facts surfaced as unverified); geometry is our six-face B-rep box at true catalog dimensions; MEP electrical connectors are genuinely written (face-referenced ConnectorElem, voltage/poles/VA domain, parameter bindings). The same constructors run under the 2025 and 2024 framing (measured via release_ctx). RFA→RFA structured edits work on our families (`rvt.convert.edit_family`); foreign families wait on #13. Loading is certified only INTO projects: Revit-born .rfa onto our bases (T2a/TB0g) and our families into pristine/user projects; our families on our composed bases remain the open cell (#16) and bare-.rfa desktop open awaits the #52 re-test.

What is thin: one type per family; local (uuid4) parameter identity instead of shared GUIDs; all balanced load booked on phase 1 and every connector 'primary'; no Electrical Fixtures product, no disconnect/generator/UPS lines; the downlight verb crashes; famspec input accepts only 'downlight'; no formulas, materials, symbolic lines, nested families, light source, hosted scaffolding or TXT type catalogs; output is non-deterministic; famgen tests skip in CI; no single family-QA call.

**Done for a user:** 'give me an Eaton PRL1X lighting panel family, 100/225 A types, for Revit 2025' returns one .rfa with named types, correct connector loads, contract parameters that bind the firm's schedules by GUID, a QA report (VALID / provenance clean / release 2025), and — once the catalog viewer round passes — a ledger entry saying Autodesk's reader accepts that shape placed in a project; the honest caveats (PROOF-ONLY until G2–G4, composed-base cell open) are printed after delivery, never instead of it.

**Staged path:** (1) hygiene now, sample-free and auto-eligible — fix the downlight, run famgen tests in CI, determinism, the QA verb with --target-version; (2) catalog depth — famspec contract for all kinds, type catalogs, connector fidelity, shared-parameter GUIDs, the Electrical Fixtures device family, a facts JSON Schema plus one new sourced line; (3) one needs-viewer family-catalog round on the passing add_to_project cell (coordinated with #103), kept separate from #16/#52; (4) later, hosted scaffolding, formulas/labelled dimensions, ImposterLight and nested annotation — each a single-variable stream after (3) certifies the base shapes.

## E. Backwards compatibility with older Revit generations

**Where we stand (evidence):** this is the axis that decides who can receive our output at all: Revit never opens a newer file, so every older release we can emit widens the audience, and every older release we can read widens what users can bring us. Where we stand, with evidence: the version model (src/rvt/versions) is sound and by-name — four releases registered, framing ordinals resolved from each file's own schema, and the first real era boundary (2023's 32-bit element ids) packaged as the reversible records32 layer, read at exact parity on six 2023 samples and viewer-certified through B2023_K4 (verdicts #31). Creation is certified for 2026/2025/2024 (composed bases bundled in the plugin); native 2025 authoring is viewer-certified, native 2024 authoring is only validator-clean; 2023 creation waits on #17's compose plus creation-side 32-bit support that release_build_context does not yet activate. The user-facing edges are behind the engine: the CLI refuses --target-version 2023/2027 outright while the library beneath it degrades honestly; a 2027 request is told 'your Revit cannot open it' (false); the standalone .rfa routes silently emit 2026 families for a 2024 request; the inspect skill crashes on any non-2026 project; the registry has no 2023 slot; the honest matrix and plugin docs have no per-release rows, and the author skill's per-release prose is already stale. Below 2023 we hold zero measured facts — only prior art (BasicFileInfo layout eras, a one-file-per-release 2016–2026 family corpus in vendor/) and the audit's own 'may already read (unverified)'.

**Done, for a user:** they name any Revit year and always get a delivered file plus one true sentence — native when that year is certified, the newest certified older release (opens by upgrade) when the year is newer, the honest fallback + IFC when it is older than everything certified; .rvt and .rfa behave identically; any existing file they hand us is read under its own release or refused up front with its detected era and the supported floor; the plugin states create/edit/read status per year in one table every skill quotes.

**Staged path:** (1) sample-free honesty now — any-year CLI, newest-certified-≤-target policy, .rfa routes honour the target, inspect/edit release-aware, older-era precheck, one release truth table with a roster test; (2) sample-free 2023 engineering — ids32 in the build context and creation chokepoints, records32 in CI; (3) gated — #17 compose + G_ABPD_2023 certification and flip, a viewer batch certifying authored 2024/2025 outputs, an owner-machine probe fixing the pre-2023 read floor; (4) repeatable onboarding — one command + checklist so Revit 2027 is a report, not a campaign of archaeology.
