# 08 — Strings & GUID orientation map

*Where do human-meaningful values physically live in a Revit 2026 `.rvt`?*

Agent: `strings-map`. Tooling: `src/rvt/strings_scan.py` (sweeps every
inflated gzip member `extracted/<file>/<Stream>.gz/NNN.bin`, the raw metadata
streams, and — new — the *raw gaps* between carved gzip members). Indexes:
`extracted/_index/strings_<file>.jsonl`, `extracted/_index/guids_<file>.jsonl`
(one JSON object per hit: `file, stream, member, offset, encoding, class,
len, len_prefixed, text, ctx`; GUID rows carry `form, guid, known`).
Default subjects: `racbasicsampleproject` (racbasic) + `rstbasicsampleproject`
(rstbasic); `--all` sweeps all six.

Offsets below are **byte offsets inside the named inflated member** (or inside
the raw stream for `[raw]` / `[rawgap]` sources). All hex is verbatim from
racbasic unless noted. Confidence markers: **[verified]** = seen in bytes,
reproducible with the tool; **[hypothesis]** = interpretation not yet proven.

---

## 1. The universal string encoding: `AString`

**[verified]** Every user-visible string in every stream is stored the same
way — a 32-bit little-endian **character count** followed by that many
**UTF-16LE code units, no NUL terminator**:

```
offset  size      field
0       4         uint32 nChars
4       2*nChars  UTF-16LE code units
```

Worked example — the type name `Wall - Timber Clad`, `Partitions/15` member
058, `+0x132dd`:

```
000132dd 12 00 00 00 57 00 61 00 6c 00 6c 00 20 00 2d 00 20 00 54 00   ....W.a.l.l. .-. .T.
000132f1 69 00 6d 00 62 00 65 00 72 00 20 00 43 00 6c 00 61 00 64 00   i.m.b.e.r. .C.l.a.d.
          nChars = 0x12 = 18  → "Wall - Timber Clad"
```

The scanner flags this with `len_prefixed: true` (the preceding u32 equals the
matched char count). In racbasic 78 % of `name`-class UTF-16 hits inside
`Partitions/15` are length-prefixed AStrings; the rest are the interior of a
longer AString the regex re-matched, JSON/XML text, or debris. A null/absent
string is written as `ff ff ff ff` (i.e. nChars = 0xFFFFFFFF) — see §6.2.

Strings are **not** aligned: AStrings routinely start at odd offsets.

## 3. `BasicFileInfo` — the metadata mirror (racbasic, 2,171 bytes)

**[verified]** Mixed layout: a 14-byte binary header, then a run of
length-prefixed UTF-16 AString fields (with a few interleaved u32s), then a
UTF-16 `key: value\r\n` text block whose two framing CRLFs are **single-byte**
`0d 0a` (at `0x263` and `0x879`) while the CRLFs inside the block are UTF-16
(`0d 00 0a 00`) — this is what puts the block at an odd byte offset and makes
a whole-stream UTF-16 decode look like garbage. Decode the AStrings by walking
`(u32 len, chars)`; decode the block from `0x265`.

| `0x01a` | AString (n=18) | `20250227_1515(x64)` — build |
| `0x042` | AString (n=70) | `C:\Users\hansonje\Desktop\Downloadable Files\racbasicsampleproject.rvt` |

## 4. Where element type/instance names live — conclusions

**[verified]** All element names (levels, grids, views, types, materials,
families, rooms) live **only** inside element records in the
`Partitions/<N>` gzip blocks, as length-prefixed AStrings. No name appears in
`Global/ElemTable` (0 UTF-16 hits — it is a pure numeric id table) and none in
`Global/History`. `Global/Latest` (the `ADocument` graph) holds *document-level*
names only (settings objects, phases, colour-fill schemes, browser
organisation, unit JSON), not element names.

## 5. Where parameter *values* live — the ProjectInformation worked example

**[verified]** Instance/type parameter values are stored **inline in the
owning element record** in a `Partitions/<N>` block as a **map of
(int64 parameter id → AString)** for text parameters. Built-in parameters use
their public Revit API `BuiltInParameter` enum value (negative int) as the key.

racbasic `Partitions/15` member **095** (raw stream offset 3,184,942;
inflated 35,075 bytes), ProjectInformation element, `+0x5580`:

```
00005580 0a 00 00 00                                        count = 10 entries
00005584 80 73 f0 ff ff ff ff ff | 08 00 00 00 "Autodesk"  (str @+0x5590)   id -1019008
000055a0 81 73 f0 ff ff ff ff ff | 00 00 00 00 ""                            id -1019007
000055ac 82 73 f0 ff ff ff ff ff | 25 00 00 00 "Samuel Macalister sample house design" (@+0x55b8)
00005602 83 73 f0 ff ff ff ff ff | 11 00 00 00 "Samuel Macalister" (@+0x560e) id -1019005
00005630 0f a5 f0 ff ff ff ff ff | 0a 00 00 00 "Issue Date"      (@+0x563c)   id -1006321
00005650 10 a5 f0 ff ff ff ff ff | 0e 00 00 00 "Project Status"  (@+0x565c)   id -1006320
00005678 11 a5 f0 ff ff ff ff ff | 08 00 00 00 "Autodesk"        (@+0x5684)   id -1006319
00005694 12 a5 f0 ff ff ff ff ff | 12 00 00 00 "Enter address here" (@+0x56a0) id -1006318
000056c4 13 a5 f0 ff ff ff ff ff | 0c 00 00 00 "Sample House"    (@+0x56d0)   id -1006317
000056e8 14 a5 f0 ff ff ff ff ff | 06 00 00 00 "001-00"          (@+0x56f4)   id -1006316
```

Entry layout: `int64 paramId` (LE, sign-extended — `0xFFFFFFFFFFF0A513` =
**−1006317**) then `AString value`. The ids equal the public Revit API
`BuiltInParameter` constants **[verified for the -1006xxx block against the
public enum: `PROJECT_ISSUE_DATE=-1006321`, `PROJECT_STATUS=-1006320`,
`CLIENT_NAME=-1006319`, `PROJECT_ADDRESS=-1006318`, `PROJECT_NAME=-1006317`,
`PROJECT_NUMBER=-1006316`]** and **[hypothesis for the -1019xxx block:
`PROJECT_ORGANIZATION_NAME=-1019008`, `PROJECT_ORGANIZATION_DESCRIPTION=-1019007`
(empty), `PROJECT_BUILDING_NAME=-1019006`, `PROJECT_AUTHOR=-1019005`]**. Every
value matches the `project.xml` inside `ProjectInformation` (`Organization_Name
Autodesk`, `Building_Name Samuel Macalister sample house design`, `Author
Samuel Macalister`, `Project_Name Sample House`, `Project_Number 001-00`,
`Project_Address Enter address here`, `Client_Name Autodesk`).

**So the authoritative parameter values are in the Partitions element
record; `ProjectInformation` (PartAtom XML) is an exported *mirror* for
indexers.** rstbasic: the same map exists (`Partitions/21` member 030
`+0xcb1`: `13 a5 f0 …` PROJECT_NAME → nChars `0` — the value is empty in the
element even though its `project.xml` says `Sample House` → the XML can be
stale relative to the element data).

Corollary: same-shaped id→AString entries recur in type records — e.g.
racbasic member 058 `+0x131c4`: `02 00 00 00 | 3a 99 ee ff ff ff ff ff → "F10"
(str @+0x131d4) | 49 96 f0 ff ff ff ff ff → "Structural Insulation Panel
Wall …" (str @+0x131e6)` (a 2-entry map: assembly code + type description)
immediately before the type name at `+0x132e1`.

## 7. GUIDs

### 7.1 Binary layout

**[verified]** Binary GUIDs use the Windows/COM `GUID` memory layout
(`uuid.UUID.bytes_le`: 4-2-2 little-endian groups + 8 straight bytes). Proof:
`e6a03f8e-9e4e-4cfc-ae41-c3c559e42d55` (BFI text) matches bytes
`8e 3f a0 e6 4e 9e fc 4c ae 41 c3 c5 59 e4 2d 55` at `Global/History+0x366`.

### 7.2 `Global/History` = episode-GUID table

racbasic (15,290 bytes inflated):

| offset | size | field | value |
|---:|---:|---|---|
| `0x00` | 2 | u16 | `0x0538` (matches other Global/* headers) |
| `0x02` | 12 | header | `01 00 00 00 00 00 00 00 00 00 00 00` |
| `0x0e` | 4 | u32 count A | `0x350` = **848** |
| `0x16` | 4×16 | GUID slots | `e340d1fc-19c1-4200-9ff0-415bc126641d` ×3, nil ×1, then the same again — **[hypothesis]** creator/owner id block (this GUID appears nowhere else) |
| `0x66` | 4 | u32 count B | `0xbe` = 190 |
| `0x6a` | 190×4 | u32[] | ascending values `d8 01, e1 01, e5 01 …` **[hypothesis]** episode → increment indices |
| `0x362` | 4 | u32 count | `0x350` = 848 |
| `0x366` | 848×17 | records | 16-byte GUID + 1 byte `0x28`; record 0 = **Unique Document GUID** `e6a03f8e-…` |
| `0x3bb6` | 4 | trailing | end (15,290) |

rstbasic: identical framing, **1,017** records, record 0 =
`34447475-c1fb-44d1-b0f8-1adaa86cdbe1` = its BFI Unique Document GUID. No table
GUID occurs anywhere else in the file except record 0 in BasicFileInfo.
**Conclusion [verified]:** BasicFileInfo's *Unique Document GUID / episode
GUID* is `History[0]`; the History stream is the ordered log of every episode
(edit session) GUID in the file's lineage.

## 12. Firm conclusions

1. **Element type & instance names live exclusively in `Partitions/<N>`
   element records** (chunk-gzipped 128 KiB blocks, plus a few uncompressed
   inter-block records), always as `uint32 nChars + UTF-16LE` AStrings. There
   is no separate string table; names are inline per element. Levels: member
   043/044; grids: 514; wall types: 058; project info: 095; asset/material
   library: 057–085; keynotes: 012–016; views/annotation types: 017, 1002–1066.
   *(Member numbering is per-file and per-save; the anchor is the record
   framing, not the member index.)*
2. **Parameter values live inline in the same element record** as an
   `int64 paramId → value` map keyed by the public `BuiltInParameter` id (or
   a positive shared-parameter id). Text values are AStrings; doubles are IEEE
   little-endian right in the record (level elevations `40 90 c1…`, wall
   widths). ProjectInformation (member 095) is the canonical decoded example.
3. **Denormalisation is normal:** referencing records carry cached copies of
   names (view records repeat `Level 1` + level ElementId 227; every view
   repeats its render settings key strings and `assetlibrary_base.fbx`). A
   writer must expect to keep duplicates consistent.
4. **`Global/Latest` = document object graph**: unit/spec ForgeTypeId JSON,
   parameter definitions (id → name), colour-fill schemes (with room-name
   entry values), browser organisations, settings names — **no element
   names**. `Global/ElemTable`, `Global/History` contain **no text**.
5. **GUIDs:** binary `bytes_le` layout. `Global/History[0]` = BFI Unique
   Document GUID (verified in racbasic 848 records and rstbasic 1,017). The
   workset GUID `e3e052f8-0156-11d5-9301-0000863f27ad` is a cross-file
   constant tying `Contents`, `PartitionTable` and partition records.
6. **`Formats/Latest` is ASCII-only** (21.5 k kept ASCII strings, 3 UTF-16):
   class names / field names / C++ types — the schema, not data.
7. **Provenance strings are abundant**: usernames (`hansonje`, `loboarch`,
   `campbes`, `zhangg`, `xuew`, `guanq`), author working directories, library
   paths, courtesy notices — mostly in `Partitions/*` file-path fields and
   `Global/DocumentIncrementTable`.

## 13. Unknowns

- The **garbled/scrambled unit-schema JSON** in `Global/Latest`
  (`"au\0\0eod,sk"`, `tnrageUni`, rstbasic `ust ofd` ×1,795): whether this is a
  real string encoding (front-coding / two-stream interleave) or an artefact
  of our carve/inflate of `Global/Latest` (racbasic member consumed 116,552 of
  117,192 raw bytes; trailing bytes undecoded). Needs the Global/Latest agent.
- Meaning of the header ids around names: `d1 0c`/`d0 11`/`3b 01`/`e3 …`
  (level records), `09 04`/`97 04` (type records), `28 0f`, `e2 …` in the
  rawgap marker records. **[hypothesis]** class ids from `Formats/Latest`.
- The `-1019xxx` and `-1140934` / `-1015223` parameter ids are labelled by
  inference; only the `-1006316…-1006321` block is checked against the public
  enum from memory. Verify against `RevitAPI.dll` docs when available.
- `Global/History` header: purpose of the 4×GUID block (`e340d1fc-…` ×3 +
  nil), the 190-entry u32 array, and the per-record trailing byte `0x28`.
- What lives in the ~2 MB of high-entropy raw gaps of `Partitions/15` beyond
  the 164 marker records (undecoded blocks?).
- racbasic wall types store a null family AString where rstbasic stores
  `"Basic Wall"` — the rule for when the family name is materialised.
- `Global/PartitionTable` ids `0x160`/`0x338` and the meaning of its 87-byte
  layout beyond GUID + name.
